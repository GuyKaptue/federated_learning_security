# FoolsGold ln(0) defect: characterisation and read-only manuscript audit (2026-11-14)

Nothing was fixed, re-run or edited for this document. Evidence: stored result files, the manuscript source `latex/manuscript_ieee.tex` (read only), and short diagnostic calls of the unchanged code (4–5 rounds, seed 0, iid; spy on `FoolsGold._alpha`, no change to any output). The diagnostic shows reachability; it does not give the rate over full runs.

## 1. The defect
`FoolsGold._alpha` (`aggregators/literature_defenses.py`, line 169 on): `a = clip(1 − max cosine, 0, 1)`; if two clients' history cosine is 1.0, or one rounding step above (1.0000000000000002), `a = 0`, `ln(0) = −inf`, and line 175 `a[~np.isfinite(a)] = 1.0` gives that client **full weight** instead of zero. Reached whenever colluders' cumulative histories are bit-identical (same row every round).

| Attacker (existing code) | Rounds triggered (4–5-round diagnostic) | TPR in the diagnostic |
|---|---|---|
| AGR-tailored (untargeted) | every real round (112 of 175 calls, calls include the attacker's own simulations) | 0.00 |
| ALIE | 2 of 4 | 0.50 |
| MIN-MAX | 3 of 4 | 0.25 |
| Sign flip | 0 of 4 (sybil weight 1 arises from low similarity, not the defect) | 0.00 |
| Static boost, norm-matched, AGR-backdoor | 0 (cosine 0.96–0.99 among colluders) | 1.00 |

**Root cause (reading of the code, intent not confirmable).** There is no comment on line 175, and the docstring (line 128) explains only the `α = 1 → 0.99` guard "to avoid infinity". After that guard, the only non-finite value that can occur is `−inf` from `a = 0`, so line 175 fires exactly on the maximal-collusion input. The line looks like a catch-all "non-finite → default full weight" that does not distinguish invalid input from a legitimate zero; the paper's formula would clip it to 0. There is no version-control history in the repository, and the original unit tests used no exactly identical sybils, so I cannot confirm what was intended. The new `FoolsGoldIndicative` clips to 0 and pins both behaviours in a test.

## 2. Loose end: what "matched exactly" means for `FL-E3-FGVAL`
Numerical comparison, per run: the `allfeat_corrected` arm (legacy similarity, corrected α = 0 clipping) against the `legacy` arm, on 60 paired runs (10 seeds × 2 partitions × 3 scenarios), metrics ASR and clean accuracy, maximum absolute difference 0.0 (exact float equality). The other checks: legacy arm vs `FL-E3-BASE` 20 pairs and vs S3-002 jitter 5 pairs, max difference ~1e-16. **Limit:** FGVAL contains only backdoor attackers, which never trigger the defect, so the 60/60 match shows that the new class changes nothing where the defect is silent. It says nothing about untargeted identical-row attackers. My earlier statement that the defect "did not change any result" was true for E3 only and was too broad; this is corrected in the Phase 4A documents (dated notes appended).

## 3. Classification vocabulary
- **wrong number**: the stored value is bad because sybils got full weight by rounding.
- **wrong experiment**: the attacker adapted to the bug, so a corrected defence would face a different attack and a corrected re-run is not comparable.

For AGR-tailored the attacker simulates the server rule before it submits (34 candidates, deepcopy of the stateful FoolsGold). Evidence for adaptation: the AGR-tailored TPR is exactly 0.000 in all 200 stored rounds (10 seeds × 20), while non-adaptive identical rows (ALIE, MIN-MAX) are flagged in about 35% of rounds. A pure rounding coin flip (about 60%) would not give 200 of 200. This is an inference from the stored data and the diagnostic; no attacker-choice log exists and I have not re-run anything. **Label: probable wrong experiment** for AGR-tailored; **wrong number only** for ALIE and MIN-MAX (fixed formulas, no simulation).

## C. Reclassification of "0 of 140"

What is affected is the effect-size column for 22 FoolsGold contrasts (AGR 11, ALIE 11), which the text points the reader to. This corrects my earlier "unknown" for row 12.
